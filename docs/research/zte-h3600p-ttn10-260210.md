# ZTE H3600P V9 / TTN.10_260210 research note

Reviewed: 2026-08-12

## Target

- ISP: Türk Telekom
- Device: ZTE ZXHN H3600P V9
- Firmware: `H3600P V9.0 TTN.10_260210`
- Privileged web administrator: blocked / research required
- Linux root shell: not supported

## Finding

No public source reviewed for this release provides a reproducible,
recovery-tested method for privileged web access or a root shell on the exact
firmware.

The current review found additional leads, but none closes that gap. The
archived H3600/H3600P project states that it is no longer maintained for newer
firmware and limits its stated range to `V9.0.0P16_TR` and earlier. The target
is identified as `H3600P V9.0 TTN.10_260210`, which is not an exact version match.
A later H3600P guide documents `TTN.8_250626`, not the target build. The July
2026 H3600P discussion says the previously known method was fixed by a recent
software update. A separate January H3600 V9 exploit repository linked from a
community guide is no longer available, and the guide's author explicitly
distinguished the H3600 method from H3600P.

The February H3600P guide also depends on an externally hosted VirtualBox
image and does not publish a verifiable image hash, source provenance, exact
target match, or recovery results. It is therefore not a safe reproducible
input for this project; its image must not be executed or reused as evidence.

The well-known older workflow is firmware-specific. It places a computer on the
router WAN side during factory provisioning, emulates the expected network
services, and attempts to influence a TR-069 session. Public code and reports
show that it targeted older data-model paths and older firmware behavior.

This cannot be generalized safely:

- account indices and TR-069 parameter paths can change;
- newer firmware may reject or authenticate the replacement management path;
- receiving a protocol response does not prove that a privileged login works;
- a factory reset can erase Internet, VoIP, IPTV, VLAN, or Wi-Fi settings;
- configuration exports can contain credentials and subscriber identifiers.

Reports mentioning `X_TTG.Users.User.2` or other vendor-specific parameter
families are leads for exact-build observation only. They are not proof that
the same parameter exists, is writable, or enables a root shell on
`TTN.10_260210`.

unidentified VM cannot promote this record to experimental or verified.

## Evidence

1. The [archived h3600-root project](https://github.com/enoymuss/h3600-root)
   says it no longer works on newer firmware and identifies an older working
   range.
2. The [older community workflow](https://forum.donanimhaber.com/zte-zxhn-h3600p-guncel-h298a-root-etkinlestirme--161912895)
   reports validation on `TTN.5_240228`, not `TTN.10_260210`.
3. A [TTN.10_260210 discussion](https://forum.donanimhaber.com/zte-zxhn-h3600p-guncel-h298a-root-etkinlestirme--161912895-3)
   reports that the method does not root the newer build.
4. A [July 2026 report](https://techolay.net/sosyal/konu/zte-zxhn-h3600p-v9-routerda-root-erisimi-nasil-alinir.204807/)
   says the recently known method was fixed by a firmware update.
5. The [H3600P V9 request in zte-config-utility](https://github.com/mkst/zte-config-utility/issues/137)
   remains open after unsuccessful backup-decoding attempts. This repository's
   offline codec can process the documented container format, but that does not
   verify the exact TTN.10 field semantics, device-specific encryption inputs,
   firmware acceptance, or recovery behavior.
6. A detailed [Digi H3600P hardware write-up](https://orca.pet/zteh3600p/)
   concerns `V9.0.0P2_DIGI` and warns that even a newer Digi build locks down
   parts of the hardware workflow.
7. ZTE's [official product page](https://www.zte.com.cn/global/product_index/smart_home_en/home_router/zxhn-h3600p/zxhn-h3600p.html)
   describes the gateway and remote-management capability but provides no
   customer root-enablement procedure.
8. Türk Telekom's [official H3600P user manual](https://www.turktelekom.com.tr/tt-destek/Documents/zte-h3600p-fiber-modem-ullanim-kilavuzu.pdf)
   identifies the device and documents a factory-reset button, but does not
   provide a firmware image, downgrade path, or root-enablement procedure.
9. The [February H3600P guide](https://techolay.net/sosyal/konu/turk-telekom-superonline-icin-zte-h3600p-nasil-rootlanir.181032/)
   points to an externally hosted VM and later records a different
   `TTN.8_250626` build; neither is evidence for `TTN.10_260210`.

## What is needed for real support

The following work must be performed on an owned or explicitly authorized
device:

1. Record the exact hardware revision and firmware string.
2. Establish and test a recovery path without publishing configuration data.
3. Observe only non-secret provisioning behavior in an isolated lab.
4. Identify the exact access level being changed.
5. Verify the change with a separate local login.
6. Confirm that Internet, IPTV, VoIP, updates, and WAN-management safety are
   preserved.
7. Repeat rollback and independent reproduction.

If a firmware `.bin` becomes available, first preserve it privately and record
its SHA-256 hash. The repository's `firmware-inspect` command can perform that
hashing and scan opaque bytes for the exact build string and recognizable
boot/kernel/rootfs container markers without executing or modifying the file:

```shell
cpe-atlas firmware-inspect \
  --input firmware.bin \
  --expected-version "H3600P V9.0 TTN.10_260210" \
  --json
```

Offline inspection can establish whether the image contains the exact build
string and recognizable containers. It does not by itself prove that the image
is flashable, unsigned, recoverable, or safe to modify; those claims require a
tested recovery path and an exact-device validation. If a hash was recorded
separately, add `--expected-sha256 <64-hex-characters>` to verify that the
artifact has not been substituted; a mismatch returns a nonzero exit code.

Do not upload `config.bin`, firmware dumps, packet captures, passwords, cookies,
certificates, serial numbers, MAC addresses, or subscriber IDs to a public
issue.

## Practical alternative

For advanced routing today, ask Türk Telekom for supported bridge/PPPoE options
and use an owner-controlled router behind or instead of the ISP gateway where
the service permits it. This avoids claiming or depending on an unverified
firmware modification.
