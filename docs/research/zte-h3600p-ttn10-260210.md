# ZTE H3600P V9 / TTN.10_260210 research note

Reviewed: 2026-10-04

A public-source follow-up on 2026-09-17 found no qualifying exact-build evidence
for configuration acceptance, service preservation, or tested recovery. The
[Digi hardware article](https://lacerta.es/zteh3600p/) remains about older Digi
firmware; its author announced the move from orca.pet on 2026-09-08. Its links
were repaired without changing the blocked support decision or resolving the
target's physical hardware revision.

On 2026-09-23, the device owner reported that the target UI showed `V9.0.7`
in a software-version field. A read-only inspection of the signed-in local
console on 2026-09-26 instead showed device type `H3600P V9.0`,
`Donanım Versiyonu` (hardware version) `V9.0.7`, and `Yazılım versiyonu`
(software version) `TTN.10_260210`. The direct observation supersedes the
earlier field attribution. It does not determine the physical hardware
revision, exact-build configuration-import acceptance, or a tested recovery
path. The catalog keeps the `H3600P V9` model, provisional `V9.0` hardware
key with unresolved status, and `H3600P V9.0 TTN.10_260210` firmware
identifier distinct. A separate report below also pairs `V9.0.7` with a
different `TTN.8_250626` build; it does not make the builds interchangeable.
An owner-supplied underside photo reviewed on 2026-09-27 confirms the printed
`ZTE ZXHN H3600P` model and a `12/2025` manufacturing date, but shows no
physical hardware revision or firmware marking. A second photo shows a
separate GPON ONT and cannot identify the gateway revision. The original
photos contain credentials and device identifiers and must remain private.
The UI's `V9.0.7` hardware-version field still has no authoritative mapping
to the provisional catalog `V9.0` key.

## Target

- ISP: Türk Telekom
- Device: ZTE ZXHN H3600P V9
- Firmware: `H3600P V9.0 TTN.10_260210`
- Privileged web administrator: blocked / research required
- Linux root shell: not supported

## Finding

No public source reviewed for this release provides a reproducible,
recovery-tested method for privileged web access or a root shell on the exact
firmware.

### October 4 source and device evidence review

The owner confirmed that the TTN.10 target is their active Internet gateway.
The retained October 1 ordinary-admin observations identify the UI firmware
as `TTN.10_260210`, hardware field as `V9.0.7`, and boot version as `V1.0.0`.
They include two encrypted type-4 configuration exports; neither has been
successfully decrypted. The advertised `rsc` view rendered a 404 page. On
October 2, the advertised `tr069` view also rendered a 404 page. These are
rendered-page observations, not verified network HTTP statuses, and cannot
prove that either backend is absent or that a privilege bypass exists.
Repeating these observations is not a replacement for obtaining the missing
server implementation or same-device configuration secret.

The [factory-mode field report](https://github.com/FuLi001/zte_modem_tools/blob/eb7ff65f16ace0c2b8ab784dd5f227c3666d8c6b/docs/g7615tv2-xe-wuhan-telecom.md)
at commit `eb7ff65f16ace0c2b8ab784dd5f227c3666d8c6b` concerns a China Telecom
G7615TV2-XE running `V3.1.0P1T1`. It starts with already authorized superadmin
credentials. Its example checks `uname -s`, which identifies Linux without
establishing UID 0. The cleanup closes client connections without confirming
that the device's temporary listener was disabled. The author reports losing
temporary access on reboot and does not demonstrate native persistence.
This supplies neither initial superadmin access nor TTN.10 compatibility.

The [H3601P OpenWrt documentation](https://github.com/wmemcmp/h3601p/blob/fa450d7be1b06d807ef6528023850bf21d4e40cc/README.md)
at commit `fa450d7be1b06d807ef6528023850bf21d4e40cc` describes another device
and a boot/flash conversion. Its complete GitHub tree contains documentation,
artwork and audit inventories, but none of the referenced `openwrt/`, `out/`
or `analysis/` implementation; the repository has no releases at this review.
The author's [UART-unlock instructions](https://techolay.net/sosyal/konu/h3601p-v9-openwrt-sureci-ve-uart-kilidi-kirilmis-bootloader-u-boot-imaji.215749/)
run a flash-writing utility from a router shell. We infer that this sequence
presupposes shell access; it does not explain how to obtain a first shell on
TTN.10. The published material cannot supply an initial-access implementation
or a reproducible firmware image for this H3600P. Its flash layout and removal
of stock fallback must not be applied to the active TTN.10 gateway.

ZTE's [alternate H3600P product page](https://www.zte.com.cn/global/home_and_enterprise/smart_home/zxhn_h3600p.html)
lists TR-064 LAN configuration. This is a generic product capability, not
an exact ISP-build account or shell method. The retained October 1
single-target unicast discovery received no accepted descriptor response.
A separately retrieved UPnP descriptor listed OS information, WAN connection
and firewall services, without a configuration service. These bounded
observations do not prove TR-064 is absent, and do not identify an account
change or configuration-secret export operation.

The fresh review found no reproducible superadmin or UID-0 method, or matching
public firmware/recovery artifact, for `TTN.10_260210`. The actionable missing
input is a provenance-bound matching firmware/filesystem implementation, the
same device's configuration-encryption input, or exact-build boot evidence
and a recoverable unit. The current CLI has no device access adapter;
`config-generate` changes a local SSH configuration template, not a router
account, and `apply` refuses device changes. Support remains blocked.

### October 2 source review

The source review adds three leads without establishing a method for this
build. The [TTN.5 H3600P responder](https://github.com/sun-net-tr/ZTE-H3600-H298A-root/blob/aa3fd17bb4799ac403b3789a0bc8df8eaffa5fdf/zte_en.sh)
uses `X_TTG` shell and account paths. A [TTN.8 variant](https://github.com/amcique/ZTE-H3600-root/blob/cb2b0592dbe2d3e1e25c1541a7ee1d263e6a4cdd/zte_en.sh)
also requests SSH enablement, but writes its success marker when emitting
`SetParameterValues`, before receiving acceptance. Neither implementation
verifies a device-originated UID. Both require provisioning and configuration
changes; their success messages cannot establish Linux root.

The [September factory-mode implementation](https://github.com/langit7/zte_modem_tools/blob/010dab9f14d6d71d9df458f233c25926b5e3d87d/zte_factroymode.py)
supports newer challenge and client-MAC proofs for other ZTE devices. Even its
challenge sequence changes factory-session state, so a partial handshake is
not a read-only applicability check. Temporary mode generates credentials and
attempts service configuration. The exact TTN.10 persistence, interface scope,
expiry and rollback behavior are unknown. Its temporary login check accepts a
shell-like prompt rather than verifying UID 0, and closing the client socket
does not prove the listener was disabled. Do not run the upstream CLI unchanged
or treat its temporary label as a preservation guarantee.

The [original HTTPD advisory](https://wr3nchsr.github.io/zte-multiple-routers-httpd-vulnerabilities-advisory/)
describes RSA/checksum stack overflows and conditional Lua-session inclusion
under CVE-2024-45413 through CVE-2024-45416. The verified model/build table does
not include H3600P or TTN.10. Client RSA helpers or an encrypted checksum header
can identify a component to investigate, but cannot establish server copy
bounds, authentication order, exploitation or a patch. Confirmation needs the
matching HTTPD executable, native libraries and Lua scripts. Malformed requests
are not a safe substitute for that implementation evidence on an active unit.

An enabled anonymous Samba setting is also insufficient: it does not establish
an active disk share, router-filesystem exposure or root privileges. The
[Samba documentation](https://www.samba.org/samba/docs/current/man-html/smb.conf.5.html)
distinguishes guest filesystem identity from the server process. Existing
advertised shares might supply an authorized artifact for offline inspection;
ordinary USB storage is not a firmware or personalization export. No exact
TTN.10 export path was established by this public-source review.

### Earlier observations

The current review found an additional public lead, but none closes that gap. The
archived H3600/H3600P project states that it is no longer maintained for newer
firmware and limits its stated range to `V9.0.0P16_TR` and earlier. The target
is identified as `H3600P V9.0 TTN.10_260210`, which is not an exact version match.
A February 2026 guide claims applicability to Türk Telekom H298A/H3600P and
Superonline H3600/H3600P, but it does not identify the target build, publish a
hash for its external VirtualBox image, or provide recovery evidence. A
follow-up reports that the guide failed on `V9.0.7` / `TTN.8_250626`, which is
still not the target build. The July
2026 H3600P discussion says the previously known method was fixed by a recent
software update. A separate January H3600 V9 exploit repository linked from a
community guide is no longer available, and the guide's author explicitly
distinguished the H3600 method from H3600P.

A newer public repository implements a DHCP/DNS/HTTP CWMP responder for the
H298A. Static review shows H298A-specific naming and vendor parameter paths;
there is no H3600P target detection, exact TTN.10 fixture, or recovery evidence.
It is useful as a protocol-research lead only, not as a runnable H3600P method.
The responder sends five `InternetGatewayDevice.X_TT.*` values through
`SetParameterValues`, including local-access, account, and shell settings. It
does not first enumerate the target data model and treats a generic
`SetParameterValuesResponse` as success. Running that payload against an
H3600P would therefore be an unverified configuration write, not a diagnostic.

A 2026-09-17 read-only follow-up against the owner-controlled TTN.10 unit found
the current local login flow. The unauthenticated HTTP page requests an
eight-character login challenge, hashes the entered password plus that
challenge with SHA-256, and posts the digest with a session token. That
algorithm is fixed by the firmware: this transform is interoperability for one
local challenge-response login, not password storage, and substituting a
password KDF would produce a value the device cannot authenticate. Its exposed
challenge and response also permit offline guessing of low-entropy passwords
when captured on the local HTTP path. Use a password-manager-generated,
high-entropy password unique to this router and run the collector only on a
trusted isolated or direct LAN; the public challenge is not a password-hardening
salt.

The exposed pre-authentication route names include the normal login,
language, time, and access-device helpers. Its inline access map advertises
`tr069`, `mirror`,
`capture`, and `rsc` at visibility level 3 and `usrCfgMgr` at level 1. The
public source contained no `InternetGatewayDevice`, `X_TT`, root, shell,
Telnet, H3600P, or exact-build string. A direct GET of the advertised `tr069`
page view while logged out returned the login page. These observations prove
that the route IDs are compiled into this web shell, but not that the standard
account can render them, that `rsc` controls a shell service, or that any field
is writable.

The CLI now includes a bounded `web-evidence` collector for that next check. It
makes one normal login attempt, fetches the authenticated root/status views,
parses the advertised page-access map, and uses GET only for the matching
`tr069`, `rsc`, user-manager, mirror, and capture views. It emits access levels,
route names, parameter names, bounded HTML field/element IDs,
configuration-object IDs, Lua resource names, and boolean marker observations.
It rejects a nominal login that still serves the login page, never prints or
saves credentials, cookies, raw responses, input values, or parameter
values, and sends no CWMP or configuration request. Its output remains
observation evidence only; it cannot promote this recipe without a reproducible
exact-build method and tested recovery.

Public H3600P hardware research also reports that the configuration-encryption
passphrase is stored in a per-device personalization area alongside other
device identity data. That explains why metadata-only inspection of the
encrypted backup cannot recover the passphrase. It is a cross-firmware hardware
lead only: whether the exact TTN.10 boot chain exposes that area, and whether a
read-only observation is possible without changing state, must be established
on a spare or recovery-tested unit.

The repaired Digi article provides more precise boundaries for that lead. Its
tested unit ran `V9.0.0P2_DIGI`, used a 3.3 V four-pin AUX3 UART at 115200 8N1,
and exposed a password-protected U-Boot prompt. The same author warns that the
newer `V9.0.0P5_DIGI` appears to lock serial. The older Türk Telekom
`TTN.5_240228` report also shows 115200-baud boot output, `non secure boot`,
`non secure uboot`, a ZX279128S SoC, and a different 512 MiB flash/RAM layout.
Those differences show why neither memory offsets nor the older fixed
bootloader password can be assumed for TTN.10. A `non secure` line by itself
also does not establish an interruptible bootloader, Linux console, or root
shell.

The CLI therefore includes an offline `uart-evidence` analyzer for the first
exact-build discriminator. It reads one bounded private capture, recognizes
allow-listed bootloader, kernel, firmware, hardware, SoC, memory, security, and
prompt markers, and emits no raw lines, file path, serial/MAC/password value, or
device command. A passive first capture must leave router VCC and RX (adapter
TX) disconnected and must not press the boot-interrupt key. The result can show
whether TTN.10 emits recognizable boot output; it cannot prove root access or
authorize a bootloader change.

Passive boot output is not the documented source of the encryption secret.
The Digi article retrieves personalization through interactive authenticated
U-Boot NAND reads; enabling full Linux logging also changes saved bootloader
state. A receive-only capture can identify boot and access readiness, but must
not be described as recovering the tag secret or authorizing those later
interactive operations.

The guide's externally hosted VirtualBox image is therefore not a safe
reproducible input for this project; its image must not be executed or reused
as evidence.

An owner-controlled read-only check of the live target's local web page
identified the exact build string `H3600P V9.0 TTN.10_260210`. The same
single-host diagnostic found HTTP/HTTPS reachable and SSH/Telnet not reachable.
The page source did not expose the H298A CWMP parameter names. Its inline
access map names gated areas such as TR-069, firmware upgrade, traffic
mirroring, packet capture, user configuration management, and an `rsc` page
whose label and semantics have not yet been observed. That earlier check
provided no authenticated field data. This is useful identity and exposure
evidence, but it does not prove the absence of hidden authenticated features
or a root method.

The well-known older workflow is firmware-specific. It places a computer on the
router WAN side during factory provisioning, emulates the expected network
services, and attempts to influence a TR-069 session. Public code and reports
show that it targeted older data-model paths and older firmware behavior.

This cannot be generalized safely:

- account indices and TR-069 parameter paths can change;
- newer firmware may reject or authenticate the replacement management path;
- receiving a protocol response does not prove that a privileged login works;
- a factory reset can erase Internet, VoIP, IPTV, VLAN, or Wi-Fi settings;
- configuration exports can contain credentials and subscriber identifiers.

Reports mentioning `X_TTG.Users.User.2` or other vendor-specific parameter
families are leads for exact-build observation only. They are not proof that
the same parameter exists, is writable, or enables a root shell on
`TTN.10_260210`.

## Expanded access-path analysis (2026-10-04)

This follow-up expands the research into acquisition, authentication, service
control, operating-system privilege and recovery. It includes new primary-source
comparisons and a synthetic digest experiment. It does not enable access on the
owner's router. The exact TTN.10 support decision remains blocked.

### Define the result before choosing a route

| Result | Evidence that would establish it | Evidence that is insufficient |
|---|---|---|
| Privileged web administrator | A separate authenticated login whose server-authorized account can use the relevant privileged operations | A changed menu, a username named `root`, or an advertised visibility level |
| SSH/Telnet service | An actual listener with known interface binding and a fresh accepted login | Generated credentials, a configuration field, or a factory acknowledgement |
| General Linux shell | Device-originated command execution outside a restricted configuration CLI | A `CLI>` prompt or the availability of a `shell` command name |
| Linux UID 0 | Device-originated `id -u` returning `0` in the established session | `uname`, an environment username, `#`, or the computer's own root privileges |
| Persistent and recoverable access | Verified behavior after boot/provisioning, preservation of services, and restoration of the original baseline | A one-session result, a saved local file, or two boot-bank markers |

These results can occur independently. Recovering an existing privileged web
credential can avoid an account edit; enabling SSH still leaves its login,
shell type and process identity to establish. A generic firmware image may
answer implementation questions while lacking the owner's personalization
secret. Conversely, a personalization secret may unlock a backup while leaving
the importer and service behavior unresolved.

### Route inventory and the next discriminator

The ranking below is an order for gathering useful evidence, not an estimated
success probability. No reviewed route is a verified TTN.10 procedure.

| Route | Potential result | Evidence needed to advance it | Current assessment |
|---|---|---|---|
| Provider/vendor-authorized account or diagnostic export | Privileged web access or matching implementation files | A supported exact-build capability, account grant or actual export | First acquisition option to investigate |
| Private backup decryption | Current account/service structure and possibly existing credentials | Same-device secret, correct derivation and complete container validation | Strong older-H3600P foundation; secret still missing |
| Minimal configuration import | Account or shell-service changes | Validated baseline, exact importer acceptance and service semantics | Separate unresolved gate after decryption |
| Isolated CWMP provisioning | Privileged account/service configuration | Accepted management session plus observed writable target paths | Older build evidence; exact transport/model unknown |
| TR-064 configuration service | Local account/configuration operations | Actual service descriptor and authorized action semantics | Generic model capability only |
| Factory/debug service | Temporary shell, potentially persistent service | Exact factory implementation, proof format, credentials and verified service effects | Source exists for other devices; initial access may be a prerequisite |
| Native HTTPD/Lua authorization or execution flaw | Privileged web operation or process execution | Matching binaries, reachable handler and complete prerequisite chain | Static research branch; no exact-target finding |
| Passive UART followed by an accessible bootloader | Board/boot evidence, then possibly implementation acquisition | Exact boot log and separate bootloader access evidence | Passive observation cannot supply the later access by itself |
| External flash acquisition | Implementation and same-device personalization without web login | Matching board/chip, reliable read, ECC/OOB/bad-block handling | Concrete independent acquisition branch on other ZTE platforms |
| Compatible temporary research boot | Linux shell independent of stock login | Accessible loader, accepted compatible image, dependencies and tested recovery | Bootloader possession alone is insufficient |
| Same-board older firmware | Potentially restore an older access path | Authenticated image, update/rollback policy and recovery-tested compatibility | No matching downgrade artifact or procedure found |
| Alternate firmware port | Owner-controlled operating system | Board support, initial installation access, calibration and recovery | H3601P material does not establish this H3600P path |

### Configuration: four separate problems

**1. Obtaining the input.** The documented H3600P derivation needs a 32-character
same-device personalization secret as well as normalized identity inputs.
Public model constants, the ordinary web password and another unit's secret do
not replace it. A matching filesystem can reveal the derivation and import
code, but a generic release image should not be assumed to contain the owner's
personalization. The older [Digi research](https://lacerta.es/zteh3600p/)
establishes this distinction on its own build.

**2. Selecting the actual codec.** [Upstream PR 84](https://github.com/mkst/zte-config-utility/pull/84)
was closed without merging on 2023-12-15, at head
`c9a87a27dc98aefefd672b73036762071688b56f`. Its author reported a faulty
SHA-256 implementation in the tested H3600P. The current upstream
[CBC code](https://github.com/mkst/zte-config-utility/blob/71391597a5fb948e294ecc06809c0cf26fad860c/zcu/xcryptors.py#L154)
at `71391597a5fb948e294ecc06809c0cf26fad860c` still uses ordinary SHA-256.
Consequently, a failure in the current generic utility cannot alone falsify a
same-device secret or establish that a firmware is undecodable.

The [author's separate codec](https://lacerta.es/zteh3600p/ztetool.py)
and this project's compatibility function reproduce the fault when the final
64-byte input block has 56–63 bytes. With the documented normalization, the IV
input has 8 prefix bytes, 17 colon-form MAC bytes and 32 secret bytes: 57 in
total. The key input has 40 fixed bytes plus the serial length, so serial lengths
16–23 can also encounter the fault. The PR author's unaffected key observation
was specific to his tested unit; the target's serial length is not assumed here.

The maintainer ran an isolated experiment using synthetic bytes only. Lengths
0, 55, 64, 119 and 128 matched standard SHA-256; 56, 57, 63, 120 and 127 did not.
A synthetic 57-byte IV input also produced different first 16 digest bytes.
This verifies the local compatibility distinction, not TTN.10's implementation
or decryption of the owner's backup. The source-reviewed `ztetool.py` text
snapshot had SHA-256
`c1ab061dc1c87422b8ef09621784eb42bf3e9770ef3ed87b3c5a9f31fd241f9e`;
that identifies reviewed text, not an authenticated firmware or release.

There is a further multi-chunk question: current upstream concatenates
ciphertext before one CBC decryption, whereas the author's codec initializes
CBC separately for each encrypted chunk. That difference matters only when
there are multiple encrypted chunks. Matching implementation or a validated
private fixture must determine the target's behavior.

**3. Validating and interpreting the result.** Require the complete expected
length, compression checksums and XML structure, followed by plausible
same-device account and service records. A recognizable header or first block
is inadequate. Determine whether credentials are plaintext, encoded, hashed
or service-specific before treating a field as a reusable login secret.
Identify records by their semantics rather than assuming that user 2, row 0,
or a numeric access level has the same meaning across operators and builds.

The older Digi account describes separate SSH service, shell-selection and
privilege settings, and separate Telnet authentication. The current local
generator changes five `SSHCfg` fields; it implements no privileged-web account
change. Its patcher selects the first SSH table row, so a validated target
baseline must establish which profile that actually represents before any
generated artifact is considered for a device. Neither a field named `Level`
nor a chosen username establishes Linux UID 0.

**4. Proving import acceptance.** The author's encode branch produces a
compressed, unencrypted type-0 container, rather than reproducing encrypted
type-4 exports. The author explicitly confirmed this
[format distinction](https://github.com/mkst/zte-config-utility/pull/84#issuecomment-3721447227).
If TTN.10 accepted type 0, a particular import might avoid encrypted
serialization, but it would not recover the current service baseline or make
future exports plaintext. No TTN.10 import evidence establishes that premise.
The upstream container's model-label field called
[signature](https://github.com/mkst/zte-config-utility/blob/71391597a5fb948e294ecc06809c0cf26fad860c/zcu/zte.py#L39)
must also be distinguished from cryptographic authorization by the updater.

### CWMP: separate transport failure from model and permission failure

The first question is whether the target enters an authorized CWMP session with
the research ACS. Only then can an isolated lab establish the implemented
parameter inventory. DHCP/DNS behavior, provisioning VLAN, ACS selection,
authentication and certificate validation are separate from whether a vendor
parameter exists. Reaching a server is not evidence that its configuration
requests are accepted. Creating that observation environment may itself need
provisioning changes; read-only RPC names do not make the entire setup passive.

The [Broadband Forum specification](https://www.broadband-forum.org/pdfs/tr-069-1-6-1.pdf)
defines `GetParameterNames` and its implemented `Writable` information, and
distinguishes invalid names (9005), types (9006), values (9007) and non-writable
parameters (9008). Its `ParameterValueStruct` member is named `Name`.
The [conformance procedures](https://cwmp-data-model-test.broadband-forum.org/06-index-test-procedures.html)
separate discovery from setting, reading back and checking persistence.
These are research discriminators; they do not establish that the target will
accept an owner-selected ACS or reveal password values.

The maintainer independently retrieved both pinned public shell scripts as
text, without execution. The
[sun-net-tr source](https://github.com/sun-net-tr/ZTE-H3600-H298A-root/blob/aa3fd17bb4799ac403b3789a0bc8df8eaffa5fdf/zte_en.sh)
contains 16 `<n>` elements and no `<Name>` elements; the
[amcique source](https://github.com/amcique/ZTE-H3600-root/blob/cb2b0592dbe2d3e1e25c1541a7ee1d263e6a4cdd/zte_en.sh)
contains seven and zero respectively. Both emit settings without
`GetParameterNames` or `GetParameterValues` discovery, and neither performs a
device UID query. Their host `$EUID` checks concern the computer running the
script. The sun-net-tr success condition searches captured requests for
`<Status>0</Status>` without an independent login or read-back.

The abbreviated XML member is an additional interoperability defect relative
to the standard. Correcting it would not establish a TTN.10 bypass, an accepted
account profile or recovery. It also cannot retrospectively explain an owner's
failed attempt without the corresponding protocol trace. The scripts are
research examples rather than qualified exact-target adapters.

A LAN TR-064 route would need its own actual descriptor, action list and
authorization behavior. The product specification's capability and the
observed ordinary UPnP services do not supply them. Likewise, a program that
emulates a subscriber device to an external provider ACS is a different
operation from local discovery; the reviewed Yettel/CETIN project cannot be
used as a Türk Telekom applicability test.

### Factory and web paths: inspect the whole dependency chain

The pinned [factory controller](https://github.com/langit7/zte_modem_tools/blob/010dab9f14d6d71d9df458f233c25926b5e3d87d/zte_factroymode.py)
distinguishes three challenge formats, including a newer proof incorporating
bridge-MAC bytes and a reconstructed key pool. It can interpret a connection
error as possible factory entry. The returned proof, service request and
subsequent login are different stages. Closing the factory client or trusting
a close acknowledgement does not independently demonstrate listener shutdown.
Persistent options reach configuration writes and service restart/reboot.
The separate [Telnet implementation](https://github.com/langit7/zte_modem_tools/blob/010dab9f14d6d71d9df458f233c25926b5e3d87d/zte_telnet.py)
accepts a shell-like prompt and has additional region/configuration
prerequisites for persistence.

The useful chain to investigate is: matching server implementation, matching
challenge/proof, accepted credentials, listener and binding, fresh shell login,
numeric UID, then actual closure/restoration. The newer G7615 report starts
with an existing superadmin account. It cannot resolve the first privileged
account on this device, and its temporary service has no TTN.10 lifecycle proof.

For HTTPD/Lua, obtain the native server and libraries together with their Lua
handlers. The [original advisory](https://wr3nchsr.github.io/zte-multiple-routers-httpd-vulnerabilities-advisory/)
has different prerequisites for checksum processing, pre-authentication RSA,
an authenticated native Lua wrapper and session-file execution. The last needs
an independent means of putting controlled content into the session directory.
No exact-target implementation establishes those prerequisites or the eventual
process UID. Browser-side RSA code and editable menu visibility do not answer
these server-side questions.

Older [H168N/H201L research](https://github.com/TasosY2K/zte-router-0day-rce/blob/3a84e5c03c67fc7cb0b06ffb168717b7bfa8c8b4/README.md)
adds legacy configuration-export and Lua/file-inclusion patterns, but some
start with an authenticated session or privileged file browsing and use other
configuration formats. They are patterns for inspecting matching code, not
portable H3600P endpoints.

### Hardware: establish the board before deriving an acquisition plan

The primary sources describe materially different hardware:

| Firsthand source | Identified build/platform | Reported flash and RAM |
|---|---|---|
| [Türk Telekom UART report](https://techolay.net/sosyal/konu/ssh-ve-uart-baglantisi-ile-shell-acma.141065/) | H3600P `TTN.5_240228`, hardware field `V9.0.3`, ZX279128S | HYF4GQ4UAACBE SPI NAND, 512 MiB flash and 512 MiB RAM |
| [Digi H3600P report](https://lacerta.es/zteh3600p/) | `V9.0.0P2_DIGI` | 128 MiB parallel NAND and 256 MiB RAM |
| [H3601P author report](https://techolay.net/sosyal/konu/h3601p-v9-openwrt-sureci-ve-uart-kilidi-kirilmis-bootloader-u-boot-imaji.215749/) | `V9.0.0P3_TN2`, hardware field `V9.0.7`, product ID 38 | W25N02KV SPI NAND, 256 MiB flash and 256 MiB RAM |

The target's UI `V9.0.7` therefore cannot establish that it shares the H3601P
board, flash geometry or boot layout. The older TTN.5 report also shows multiple
image locations and personalization/calibration areas. Those observations do
not demonstrate restoration after damage to a bootloader or identity area.
No target chip identification or exact boot trace has resolved these questions.

External flash reading is an acquisition route that can be independent of
web credentials. Its applicability begins with the actual chip and electrical
interface, not a copied memory offset. In pinned
[ufprog chip support](https://github.com/hackpascal/ufprog/blob/17adf9f43c16cb18c57e270a624edc6014871384/flash/nand/spi-nand/vendor-heyangtek.c#L161),
the TTN.5-reported HYF4GQ4UAACBE has JEDEC `c9 d4`, 4-Gbit organization,
4,096-byte data pages, 256-byte OOB and a 14-bit-per-512-byte ECC requirement.
This is a concrete implementation lead for that chip, not a prescription for
the unobserved TTN.10 board.

The older TTN.5 boot log prints an 8-bit ECC capability, while the programmer's
part entry declares 14 bits per 512 bytes. These are different implementation
reports, not proof of equivalent correction or OOB interpretation. The actual
controller/chip configuration and data representation must resolve that
difference before a reconstruction is treated as reliable.

The maintainer also reviewed the relevant reader implementation. Its
[setup](https://github.com/hackpascal/ufprog/blob/17adf9f43c16cb18c57e270a624edc6014871384/flash/nand/spi-nand/spi-nand.c#L1280)
changes protection/configuration registers; that does not itself erase or
program the flash array. Ordinary reads later enable ECC, while raw mode is a
distinct choice. The
[file-read call](https://github.com/hackpascal/ufprog/blob/17adf9f43c16cb18c57e270a624edc6014871384/program/spi-nand/ufsnand-common.c#L825)
passes an ignore-ECC-error flag. The
[NAND core](https://github.com/hackpascal/ufprog/blob/17adf9f43c16cb18c57e270a624edc6014871384/flash/nand/core/nand.c#L318)
still checks and reports ECC but can continue after an uncorrectable page.
Consequently, a completed file is not proof that every byte is recovery-grade.

A future authorized acquisition must retain chip/geometry, data-versus-OOB
representation, ECC corrections and unresolved errors, bad-block handling,
physical-versus-logical addressing and stable reread evidence. The
[Linux NAND documentation](https://docs.kernel.org/driver-api/mtdnand.html)
explains why bad-block markers and OOB/ECC layout matter. A data-only logical
dump, an extracted rootfs and a vendor upgrade file have different restoration
properties; none can automatically substitute for another.

### UART, research boot, downgrade and alternate firmware

Passive boot text, an interactive bootloader and a Linux shell are three
different outcomes. The documented personalization reads on older H3600P
hardware required authenticated interactive access. A passive capture can
identify boot behavior; it cannot establish that access or recover the secret
by itself.

The [firsthand F680 report](https://blog.rop.la/en/reversing/2024/06/21/two-ways-dump-firmware-zte-zxhn-routers-part1.html)
provides a useful counterexample: despite an accessible bootloader, an attempt
to select `/bin/sh` as init failed with a kernel panic. Firmware acquisition
then used active bootloader page output. This is another model/build, but it
shows why a boot prompt cannot be equated with a successful Linux shell.
The [kernel init documentation](https://docs.kernel.org/admin-guide/init.html)
identifies filesystem, executable and interpreter dependencies to inspect.

A compatible temporary image would additionally require the right memory map,
device tree, drivers, console and storage interpretation. Booting such an image
does not preserve the stock gateway's running services. A return to the stock
boot path must be demonstrated separately on recoverable hardware.

Firmware analysis must distinguish decryption, integrity and authorization.
The [U-Boot verified-boot model](https://docs.u-boot.org/en/latest/usage/fit/verified-boot.html)
and [signature documentation](https://docs.u-boot.org/en/latest/usage/fit/signature.html)
distinguish hashes from trusted signing keys. These explain questions to ask;
they do not establish that TTN.10 uses FIT. ROM, loader and updater enforcement
can differ. An old `non secure` marker or a web RSA key cannot establish a
current upgrade-signing policy. A downgrade also needs same-board compatibility
and any rollback restrictions, followed by service and recovery verification.

The H3601P material begins from an existing router-side shell/custom recovery
environment. Its published tree lacks the referenced image-building
implementation and its layout repurposes stock fallback. It is therefore a
porting lead after initial access and board support are solved. Upstream
[CMCC A10 support history](https://lists.infradead.org/pipermail/lede-commits/2025-March/024601.html)
explicitly distinguished unsupported ZX279128 variants despite similar model
names. CPU architecture alone does not establish usable board drivers.

### Adjacent-device success and failure must remain separate

In the [H6645P V2 firsthand account](https://forum.fibra.click/d/75787-trovare-credenziali-admin-e-sbloccare-h6645p-v2/8),
an external SPI NAND read supplied same-device configuration material after
UART-shell attempts failed. Later posts describe backup decryption, recovery
of existing privileged web credentials, and then an authenticated factory
debug session. This is an acquisition-to-account-to-debug chain on another
platform. Retrieved identity text names `root` and mentions `id`, but does not
display a numeric UID result that this project independently verified.

The separate [Samba follow-up](https://forum.fibra.click/d/75787-trovare-credenziali-admin-e-sbloccare-h6645p-v2?page=3)
proposed argument handling in `cpsd` as a hypothesis; posts 42–44 proceed from
an untested idea to validation rejection and reported failure. It cannot be
credited for the other access result. A TTN.10 static investigation would need
its actual setter, validation, database propagation, argument construction and
service identity. No injection request was sent to the owner device.

Some later forum pages were accessible only through indexed primary-post text.
No private dump, configuration or linked image was retrieved. This limits
reproduction claims and prevents treating an author's successful banner as
independent exact-target proof.

### The linked video and other misleading shortcuts

YouTube's own [metadata](https://www.youtube.com/oembed?url=https%3A%2F%2Fwww.youtube.com%2Fwatch%3Fv%3DG1BrJW67SMQ&format=json)
identifies the owner's video as *ZTE Modem Root Yetkisi Elde Etme* by Technopat.
The maintainer verified metadata, not playback or the content at 186 seconds.
The related [first-party written guide](https://www.technopat.net/sosyal/konu/zte-modem-root-yetkisi-elde-etme.1523050/)
describes a configuration workflow tested on H298A V1.0 and a 2022 update
without an H298A V9 method. That written evidence cannot establish H3600P
TTN.10 support; the video timestamp is not treated as an exact-build test.

Changing browser JavaScript can reveal controls without changing server
authorization. WPS/Wi-Fi credential techniques establish network access, not
Linux UID. PPPoE credential recovery can help use a separate router, but it
does not elevate the ISP gateway. Existing SSH plus `sendcmd` is a post-access
operation, so it cannot solve initial access by itself. JTAG, ROM exploitation
and fault injection have no reviewed exact-target implementation that would
justify presenting them as usable alternatives here.

### Best next research stage

The next stage should acquire evidence that distinguishes routes rather than
repeat old login or menu checks:

1. **Supported acquisition:** establish whether the actual UI offers firmware,
   logs or a support export; identify its contents before assuming that it
   includes implementation or personalization. Ask the provider for a supported
   privileged account, exact-build image or recovery procedure if available.
2. **Exact-version source request:** ZTE's
   [official source portal](https://opensource.ztedevices.com/)
   publishes a request channel for covered open-source components when a device
   is absent from its list. Its advertised Wireless Home Gateway catalog had
   132 entries and no H3600P entry in this bounded review. This does not prove
   source is unavailable. Identify H3600P and `TTN.10_260210`, requesting the
   corresponding kernel, applicable U-Boot/board configuration, drivers and
   build instructions. The portal does not promise proprietary HTTPD/CPSD,
   signing material or the owner's secret. No request was sent.
3. **Offline implementation review:** bind any obtained artifact to origin,
   build and SHA-256; distinguish bootloader, kernel, rootfs, updater and
   personalization. Inspect account authorization, credential representation,
   codec, accepted import types and service startup/binding. Use these findings
   to choose one candidate rather than send guessed fields.
4. **Independent acquisition if needed:** on a matching spare or
   recovery-tested unit, identify boot behavior and actual flash hardware.
   Determine whether authenticated bootloader reading or a validated external
   read can supply implementation and the same-device secret. A matching spare
   supplies its own secret, not the active gateway's.
5. **Controlled validation:** after a route's prerequisites are established,
   test a minimal change against the validated baseline. Prove privileged web
   login and Linux UID independently, then listener scope, persistence,
   restoration and preservation of the subscribed services.

The existing pending firmware/UART and export-menu answers affect this next
experimental stage. Their absence does not prevent this research comparison
from being delivered. The research has identified additional discriminators;
it has not established an executable TTN.10 access method or changed the
gateway.

## What is needed for real support

The following work must be performed on an owned or explicitly authorized
device:

1. Record the exact hardware revision and firmware string.
2. Establish and test a recovery path without publishing configuration data.
3. Observe only non-secret provisioning behavior in an isolated lab.
   Use a spare or recovery-tested unit; do not factory-reset the active modem.
4. If physical access is used, begin with a passive RX-only UART boot
   observation, leaving VCC and adapter TX disconnected. Preserve all
   personalization data locally; never publish device keys, identity records,
   or credential-bearing dumps.
5. Identify the exact access level being changed.
6. Verify the change with a separate local login. A claimed Linux root shell
   must return a device-originated `id -u` result of `0`; a web administrator
   account, protocol acknowledgement, root username or shell-like prompt is
   insufficient. Synthetic/local output is not device evidence.
7. Confirm that Internet, IPTV, VoIP, updates, and WAN-management safety are
   preserved.
8. Repeat rollback and independent reproduction.

If a firmware `.bin` becomes available, first preserve it privately and record
its SHA-256 hash. The repository's `firmware-inspect` command can perform that
hashing and scan opaque bytes for the exact build string and recognizable
boot/kernel/rootfs container markers without executing or modifying the file:

```shell
cpe-atlas firmware-inspect \
  --input firmware.bin \
  --expected-version "H3600P V9.0 TTN.10_260210" \
  --json
```

Offline inspection can establish whether the image contains the exact build
string and recognizable containers. It does not by itself prove that the image
is flashable, unsigned, recoverable, or safe to modify; those claims require a
tested recovery path and an exact-device validation. If a hash was recorded
separately, add `--expected-sha256 <64-hex-characters>` to verify that the
artifact has not been substituted; a mismatch returns a nonzero exit code.

If a private passive UART capture is available, inspect it without publishing
the raw log:

```shell
cpe-atlas uart-evidence \
  --isp "turk-telekom" \
  --model "H3600P" \
  --hardware-revision "V9.0" \
  --firmware "H3600P V9.0 TTN.10_260210" \
  --input h3600p-uart-private.log
```

The report intentionally separates an exact firmware string, recognizable
H3600P boot output, an interrupt prompt, a bootloader shell prompt, and a UID-0
marker. None is inferred from another, and none causes a device write.

Do not upload `config.bin`, firmware dumps, packet captures, passwords, cookies,
certificates, serial numbers, MAC addresses, or subscriber IDs to a public
issue.

## Practical alternative

For advanced routing today, ask Türk Telekom for supported bridge/PPPoE options
and use an owner-controlled router behind or instead of the ISP gateway where
the service permits it. This avoids claiming or depending on an unverified
firmware modification.
